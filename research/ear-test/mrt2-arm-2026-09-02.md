# Arm 3 — Magenta RealTime 2 (`mrt2_small`), local on the Mac mini

Date: 2026-09-02. Model: `google/magenta-realtime-2`, size `mrt2_small` (230M), MLX backend,
`magenta-rt` 2.0.3. Machine: always-on Mac mini, base M4, 24 GB, macOS 26.3.1.

**No listening judgement appears in this file.** The agent that wrote it cannot hear. Every claim
below is an `ffmpeg` (EBU R128) or `librosa` 0.11 measurement, or a fact read out of the model's own
source. Whether any of these clips is pleasant is still an open question for the ear test.

Audio is not committed. The twelve renders live in
`~/Documents/AI Agent Outputs/Artifacts/flow-audio-candidates/` as `mrt2-<palette>-<n>.wav`
(48 kHz stereo 24-bit originals), with `-coldstart` variants beside them and 44.1 kHz matched
copies in `44k/`. No reference audio was ever embedded, uploaded or shown to the model — every
prompt in this arm is text.

## 1. Install

Everything is a prebuilt wheel. No compiler invocation, no Homebrew, no `sudo`, nothing outside the
user's home directory.

```bash
ssh cyrus@cyruss-mac-mini-1.tail976740.ts.net
mkdir -p ~/mrt2 && cd ~/mrt2
uv venv --python 3.12                 # uv fetched cpython-3.12.13-macos-aarch64 (23.8 MiB)
uv pip install "cmake<3.28"           # -> cmake 3.27.9
uv pip install "magenta-rt[mlx]"      # 41 s wall, all wheels
uv pip install "mlx==0.31.1" "mlx-metal==0.31.1"   # REQUIRED — see below
mrt models init                       # 3 m 02 s, MusicCoCa + SpectroStream
mrt models download mrt2_small        # 58 s, 455 MB .mlxfn + 8.7 MB state
```

Resolved versions: `magenta-rt` 2.0.3, `jax`/`jaxlib` 0.11.1, `numpy` 2.3.5, `librosa` 1.0.0,
`soundfile` 0.14.0, `sentencepiece` 0.2.2, `cmake` 3.27.9. Assets land in
`~/Documents/Magenta/magenta-rt-v2/` and total ~1.7 GB with `mrt2_small` only.

`cmake<3.28` is in the README under **C++ App Development**, not the Python path. The Python/MLX
path used here does not need it; installing it is harmless and costs 8 s.

### The one real problem: an undocumented `mlx` pin

`uv pip install "magenta-rt[mlx]"` resolves `mlx`/`mlx-metal` to **0.32.2**, and the model then
refuses to load:

```
File ".../magenta_rt/mlx/system.py", line 527, in __init__
  self._fn = mx.import_function(mlxfn_path)
RuntimeError: [import_function] Invalid string size.
```

The failure is not a bad download — the 455 MB file is complete. The first bytes of
`mrt2_small.mlxfn` carry the exporter's version string, and it is `0.31.1`:

```
00000000: 0600 0000 0000 0000 302e 3331 2e31 0200  ........0.31.1..
```

MLX 0.32's `import_function` cannot read a container exported by 0.31. **Pinning
`mlx==0.31.1` and `mlx-metal==0.31.1` fixes it outright**; nothing else changed. The repo does not
state this constraint and `magenta-rt`'s own dependency range does not enforce it, so anyone
installing today hits it. Worth an upstream issue.

No HuggingFace token is needed — the weights are not gated. Unauthenticated downloads work and only
print a rate-limit warning.

### `mrt2_base` was not tried, deliberately

`mrt2_base` (2.4B) was downloaded and then **deleted without ever being run**. The mini is a base M4
with 24 GB that also hosts always-on production jobs; Google documents `base` as needing a Pro/Max
chip, and an out-of-memory event on that machine would take production down with it. The whole arm
is therefore `mrt2_small` only, and **every negative finding below is a finding about the small
model, not about MRT2 as a family.** The quality gap between 230M and 2.4B is unmeasured here.

## 2. Speed

M4 (base), `mrt2_small`, `.mlxfn` graph, MLX Metal:

| | measured | real-time bar |
|---|---|---|
| 8 s smoke test | 60.5 steps/s, 16.5 ms/step | 25 steps/s, 40 ms/step |
| sustained 60 s render, 1 s state-threaded segments | 24.2–25.2 s of compute per 60 s of audio | — |
| **throughput** | **2.38–2.48× real time** | 1.0× |

Model load plus five warm-up steps is 1.2 s the first time and ~0.2 s afterwards. So a 60-second
clip costs about 25 seconds of mini time and generation is free thereafter — no API, no per-second
billing, no network. That is the single strongest thing this arm has going for it.

## 3. What the API actually exposes

Read from `magenta_rt/mlx/system.py` and `magenta_rt/cli/mlx_commands.py`, not from docs:

- CLI `mrt mlx generate` takes `--prompt --model --duration --bits --temperature --top-k
  --cfg-musiccoca --cfg-notes`. **There is no tempo or BPM parameter anywhere**, no seed, and no way
  to change the prompt mid-clip. BPM can only be asked for inside the text string.
- The Python API is what makes steering possible:
  `mrt.embed_style(text, use_mapper=True, seed=N)` returns a 768-dim L2-normalised MusicCoCa
  embedding, and `mrt.generate(conditioning={...}, frames=N, state=state) -> (Waveform, state)`
  hands back the streaming state. Threading that state across calls lets the style embedding change
  between segments with no seam in the audio — that is the mechanism behind the "prompt mixing"
  feature in Google's apps, and it is what this arm used for the crossfade clips.
- `seed` only feeds the pMF mapper that samples an audio-space embedding from a text embedding, so
  it is the variation knob for a fixed prompt.
- **There is no user-supplied negative prompt.** In `_build_graph_args` the CFG negative branch is
  the *masked* (unconditional) style, not a second string. So "no vocals, no drops, no build-ups" in
  a prompt is just more positive text handed to a contrastive text encoder, which has no mechanism
  for negation. Treat every "no X" below as decoration, not control.
- Drum control exists but only as a binary: drum-unconditional versus drumless, via the drums CFG
  scale. The model card's own text says frame-accurate drum control "is infeasible in practice".

## 4. Prompts and steering modes

Two clips per palette hold one style embedding constant for the whole 60 s (differing only in mapper
`seed`); the third crossfades linearly between two embeddings, renormalised and re-tokenised once per
second across the clip. Sampling was left at the library defaults for all six: temperature 1.3,
top-k 40, CFG musiccoca 3.0, notes 1.0, drums 1.0.

**Palette A, held (a-1 seed 0, a-2 seed 7):**
> hypnotic monotone minimal techno at 120 bpm, steady dry four-on-the-floor kick, deep sub bass, one filtered chord held throughout, no melody, no vocals, constant intensity, no build-ups, no drops

**Palette A, crossfade (a-3), from → to:**
> minimal techno at 120 bpm, dry steady four-on-the-floor kick, deep sub bass, no melody, no vocals, constant intensity
>
> monotone hypnotic minimal techno at 120 bpm, one filtered chord pad, deep sub bass, no melody, no vocals, no build-ups, no drops

**Palette B, held (b-1 seed 0, b-2 seed 7):**
> dub techno at 116 bpm, deep sine sub bass locked to the kick, a hypnotic two note motif through a tempo synced dub delay, one key, no chord changes, low-passed old school rave chord stabs pushed far back in the mix, distant muted reverb soaked trumpet pad, no risers, no drops, no vocals

**Palette B, crossfade (b-3), from → to:**
> dub techno at 116 bpm, deep sine sub bass locked to the kick, hypnotic two note motif through a tempo synced dub delay, one key, no chord changes, no vocals
>
> dub techno at 116 bpm, distant low-passed old school rave chord stabs far back in the mix, muted reverb soaked trumpet pad, deep sub bass, one key, no risers, no drops, no vocals

### The cold-start ramp, and why there are two sets of six

The first six renders started the model from its zero state and kept everything. All but one ramp
*upward* across the clip — head-3 s to tail-3 s differences of **+5.6 to +26.6 dB**. That is not an
arrangement choice; it is the model climbing out of an empty context. The fix is to generate a
throwaway prefix. The second set of six is identical in prompt and seed but **discards the first
30 s** and keeps the following 60 s. Those are the deliverable `mrt2-<palette>-<n>.wav`; the
originals are kept as `-coldstart` so the effect stays visible. With the prefix discarded the
head-to-tail spread falls to −8.7…+14.3 dB — better, and still nowhere near the references' ±3 dB.

**Practical rule for this model: never ship the first ~30 s of a render.**

## 6. What fell outside the envelope

**Tempo: total failure, and this is the headline.** Not one of the twelve renders landed near the
BPM in its prompt. Palette A asked for 120 and got 107.7, 126.0, 126.0 and 143.6; Palette B asked for
116 and got 95.7, 129.2, 136.0, 139.7 and 156.6. Errors run from −20 to +41 BPM. This is the exact
axis where the ElevenLabs arm passed — six of six inside 1.5 BPM — and the reason is structural, not
prompt-craft: **`mrt mlx generate` has no BPM parameter, MusicCoCa is a contrastive text encoder,
and "116 bpm" is just a token sequence to it.** Any product built on this model would have to get
tempo from something outside the model.

The grid is also looser. Beat-interval CV is 0.061–0.088 on eleven of twelve clips against 0.019 and
0.027 for the references — roughly three times less steady. Only warm a-3 (0.020) matches. In most
clips the dominant tempogram peaks sit at 180–290 BPM, i.e. the analyser cannot find one clean
periodicity at all.

**Constancy: fails, and only intermittently recoverable.** The target is LRA ≤ 4 LU. Two of twelve
renders meet it (warm a-3 at 1.5 LU, warm b-2 at 3.7 LU). The rest run 5.1–22.5 LU. Per-10 s RMS
range tells the same story: references 5.4 and 6.3 dB, clips 1.1–24.2 dB.

**Low end: unpredictable in both directions.** ElevenLabs failed this axis consistently — always too
much sub. `mrt2_small` fails it *incoherently*. Warm a-3 puts 98.1 % of its energy under 150 Hz;
warm b-1 puts **1.1 %** under 150 Hz and 93.8 % in the 500 Hz–2 kHz band. The same Palette B prompt
at seed 0 versus seed 7 produced 1.1 % and 38.6 % sub-150 energy. The mapper seed moves the spectral
balance more than the prompt text does.

**Body region: fails except by accident.** ref01 has 46.5 % in 150–500 Hz. Ten of twelve clips are at
1.5–14.0 %. Only b-3 (65.2 % cold, 43.0 % warm) reaches it, and there it overshoots into a mix with
almost no bass at all.

**Brightness: passes.** Every clip keeps 2–8 kHz under 1.9 % and >8 kHz under 0.25 %, against the
references' 0.44 % and 0.11 %. Nothing here is harsh in the measurable sense.

**Event density: passes.** 169–435 onsets/min around the references' 393 and 346. Only warm b-2
(435) is over the ~400 ceiling and only warm a-2 (169) is dramatically under.

**Clipping.** Both seed-7 renders (a-2, b-2) hit a 0.0 dBFS sample peak — the model saturated its own
int16 output. Any pipeline using this needs headroom management on the way out.

## 7. Can it do "no drops, no vocals, constant"? — objectively

**Constant: no, not reliably.** Objective decomposition:

- *Level.* LRA of 1.5–22.5 LU against a 4 LU target; ten of twelve renders outside it. Per-10 s RMS
  range up to 24.2 dB against the references' 5.4–6.3 dB.
- *Onset-rate variance.* Onsets-per-10 s CV runs 0.147–0.389. ref01, the track Daniel calls perfect,
  sits at 0.117 — **every single clip has more event-density drift than ref01**, and half exceed even
  ref02's 0.248. Warm b-2's onset counts go 63 → 91 → 83 → 85 → 62 → 51 across the minute; that is a
  measurable swell and decay, which is what a "build-up" looks like in numbers.
- *Spectral centroid variance.* 1 s-smoothed centroid CV is 0.33–0.82 against the references'
  0.41–0.46. Five clips (0.66–0.82) drift far more in timbre than either reference; two (0.33, 0.35)
  drift less, i.e. they are *frozen* rather than gently alive.
- *Silence and dropouts.* References: 0.00 % and 1.09 % near-silent frames. Clips: 0.04 %–15.25 %.
  Cold b-3 spends 15 % of its length more than 40 dB below its own median, and warm a-3 spends 8.9 %.
  Those are holes in the audio, not a quiet passage.
- *Fades.* No clip fades *out*. The characteristic artifact is the opposite — a cold-start ramp *in*,
  up to +26.6 dB. It is fully removable by discarding a warm-up prefix, which is the one failure mode
  in this whole arm with a clean, cheap fix.

**No vocals: cannot be established here, and I will not claim it.** I cannot hear the clips. The only
supporting evidence is indirect and weak: every clip keeps 2–8 kHz energy under 1.9 %, which is where
vocal presence would show, and Google states the training set is ~71k hours of *mostly instrumental*
stock music and that observed vocal output "tends to be non-lexical". That is a plausibility
argument, not a measurement. It needs a human ear.

**"No drops" as a prompt instruction: inert.** There is no negative-prompt mechanism in this model —
the CFG negative branch is the unconditional style, not a user string. "no drops, no build-ups,
no vocals" reaches a contrastive text encoder that has no representation of negation. The measured
build-ups above are consistent with those words doing nothing.

### Loop-ability and what the receptive field implies

Both model sizes have a **20 s effective receptive field** (`small`: 41-frame sliding-window
attention per layer × 12 layers). Two consequences, and they point opposite ways:

1. **A 60 s render cannot be butt-spliced into a loop.** At the 60 s mark the model has no access to
   anything from the first 40 s; head and tail are statistically unrelated. The measured head-to-tail
   level differences (up to 26.6 dB) confirm there is no return to the opening state. Anyone wanting a
   loop from this model would have to render, then find a matching splice point, then crossfade.
2. **But the model does not want to be looped.** `generate()` returns its state, so the natural use is
   an endless stream: keep calling, keep threading state, change the style embedding whenever you
   like. At 2.4× real time on a base M4, one mini can sustain roughly two live streams. **For a
   product that plays continuously for a 3.5-hour work block, "no loop" is a feature, not a defect** —
   and palette rotation becomes an embedding crossfade rather than a track change. That is the
   genuinely interesting capability this arm surfaced, and it is one no hosted API on the list offers.

### Hold versus crossfade

The crossfade clips are not uniformly better or worse, but the two renders that met the LRA target
(warm a-3 at 1.5 LU, and warm b-2) include one crossfade, and warm a-3 also has the only
reference-grade beat stability in the set (CV 0.020). Against that, warm a-3 has the worst spectral
balance in the set (98.1 % under 150 Hz) and 8.9 % near-silent frames. **Six clips is too few to
separate the steering mode from the seed**, and the seed-to-seed spread inside the held pairs is
larger than the hold-versus-crossfade spread — which is itself the finding: at this model size,
output variance swamps prompt-steering variance.

## 8. Licence facts worth flagging

From the model card and the repo, both captured in `research/production-options/`:

- **Code is Apache 2.0; weights are CC-BY-4.0.** The weights are *not* gated on HuggingFace — no
  token, no click-through, no account.
- **"Google claims no rights in outputs you generate using Magenta RealTime 2. You and your users are
  solely responsible for outputs and their subsequent uses."** This is materially different from the
  ElevenLabs arm, where output rights are tiered by subscription plan. There is no per-generation fee,
  no plan gate on commercial use, and no ongoing dependency on a vendor staying in business.
- **CC-BY-4.0 on the weights means attribution travels with them.** Shipping the model inside an app
  requires attributing Google DeepMind and reproducing the licence notice. That is a packaging
  obligation, not a restriction on the music. If the model runs on our own servers and only audio
  ships to users, the attribution obligation attaches to our deployment rather than to the audio.
- Usage terms additionally require not generating content that infringes others' rights, and disclaim
  all warranties. Training data is stated as ~71k hours of stock music from multiple sources.
- Everything runs offline. No audio, prompt or telemetry leaves the machine.

## 9. Where this leaves arm 3

Objectively, on the axes the spec defines, `mrt2_small` is **behind the ElevenLabs arm on every
measurable target except brightness and event density**, and it fails the one axis ElevenLabs
cleanly passed (tempo). The failures are not prompt-craft problems: there is no tempo control and no
negation mechanism in the model, so no rewrite of the palette text will fix them.

What it has instead is a different shape of value — free unlimited local generation at 2.4× real
time, unencumbered outputs, offline operation, and a streaming state API that makes continuous
never-repeating playback with smooth palette crossfades natural rather than difficult.

Three things would have to be true for this arm to survive, and none is settled by measurement:

1. The clips have to sound acceptable to Daniel in the blind test, despite the numbers.
2. Tempo would have to come from outside the model — the MIDI/note conditioning channel is the
   obvious candidate and was not exercised in this arm.
3. `mrt2_base` would have to be evaluated on hardware that can hold it, since every negative here is
   a 230M-parameter finding.
